## Database rules (Gatherwell)
- Team creation and joining go through create_team / join_team_by_code / get_team_invite RPCs so slugs, join codes and roles are set server-side.
- Active team is stored on profiles.active_team_id (falls back to first leader team, then first team), so the choice follows the person across devices; account deletion goes through delete_my_account(), which refuses while the caller is a team's sole leader.
- A deferred constraint trigger keeps at least one leader per team; transfer_leadership swaps roles and ownership in one transaction, and a guard trigger blocks clients from changing plan, owner or parent team.
- team_tree(root) is the single source for sub-team listings and calendar scope: leaders get the whole subtree, everyone else only their own team.
- Templates launch only through launch_template(), which creates the event, copies the checklist into host-only event_checklists, bumps launches_count (clients can't edit it) and writes the single "launched" win; starter templates have no team and are copied with copy_starter_template().
- Leader Insights come only from the leader-checked team_insights() RPC (activity counts, never sales) and shout-outs only from post_shoutout(); the maps key is served by a signed-in server function and the UI falls back to a placeholder plus list when it is missing.
- Gatherings are created only through create_gathering_at()/create_gathering() (one row or an 8-week series sharing series_id, one win per creation, template checklist copied) and edited through update_gathering() (one date or this-and-later in the series); the UI calls events "gatherings" and the Events tab reads ?tab=upcoming|hosting|past.
- Freed spots promote the waitlist via the rsvp_freed trigger, and guest milestones (10/25/50) come from a trigger; messages are queued as 'pending' through enqueue_message(); queue_rsvp_reminders() owns 24h/2h reminders and rsvp/event triggers reschedule or skip them; claim_outbox() applies opt-outs, suppressions and preferences before sending.
- Check-in, walk-ins, polls and the after-gathering summary go through host-checked RPCs (check_in_code, check_in_rsvp, add_walk_in, create_poll, event_summary); check-in wins are grouped into one activity row per gathering per 12 hours.
- Learn content (tracks, lessons, recipes) is read via can_use_team_templates so sub-teams inherit parent content; live meeting links live in leader-only lesson_live_links and reach members only via live_lesson_link() from 10 minutes before start; track_completed wins and live session reminders are queued by trigger; leader progress comes only from track_progress() counts.
- Challenges: check-ins only via challenge_check_in() (today, or yesterday before local noon, joined members only); others' check-ins are never readable — leaderboard (names, counts, streaks), joined counts and leader stats come from challenge_leaderboard/challenge_counts/challenge_stats; joins (grouped per 12h), 7-day streaks and finishers are trigger-written wins; encouragement only via post_challenge_encouragement(); progress photos sit in private challenge-photos under <user_id>/, owner-only.
- Recognition: automatic badges come only from evaluate_badges() run by triggers on events, rsvps, activity and team_members (once per user/badge/team, one badge_earned win each); leader awards, Host of the Month and shout-out pin/hide go through award_badge/name_host_of_month/moderate_shoutout; shout-outs only via give_shoutout(), which rejects health/weight/income claims with has_blocked_claim(); inviters are recorded through join_team_by_code(_by) for Welcome Committee.

- Network: host connections, shares, team features and guest referrals go only through network_* RPCs and record_referral(); referral credit is for guests attending gatherings, never team recruiting.
- Offer purchases come only from join_free_offer() or the Stripe webhook; members-only access is checked in the database.
- Welcome points: earned only by the first-check-in trigger, redeemed only via redeem RPCs; guests act through their RSVP code.
- Playbook: nightly compute_playbook() writes anonymized patterns (>=20 gatherings, >=5 teams) to playbook_patterns; UI reads only playbook_cards()/team_benchmark(), which return labeled samples until data suffices.
